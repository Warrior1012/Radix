## 7. Design decisions log (add as decided; keep consistent)
- Category joins are **always by `category_code`**, never by position.
- Proficiency `level` is a *separate, user/assessor-supplied* value. Extraction never sets it. Unassessed = `null` (accept legacy `0` on input and normalise to `null`). *(To be confirmed in Phase 3/4 and reflected in contract doc.)*
- Fallbacks are allowed only when `DEMO_FALLBACK=true`, and the response must carry `processing_path` naming it.
- `requirement_type` precedence: inline marker > section heading > model value > default `required` (ambiguity never silently becomes preferred). Each skill carries `requirement_basis`. These are extension fields on the skill object (the 4 contract fields are untouched); the persisted `skills` jsonb stores them without any migration.
- Route handlers stay in `app.py` for now; later phases that need to patch should patch the *module that owns the logic* and update the old tests accordingly (note it in the log).
- `xfail(strict=True)` tests in `tests/test_contract.py` mark open defects; when you fix one, delete its marker (the run fails until you do).
- Official 3-company snapshot is the default Talent Check benchmark; Supabase catalog is a labelled extension (`source: supabase`).
- **(Phase 3) Unassessed level = key absent / `null`.** Resume parsing never emits `level`. Phase 4's Profile model must normalise legacy `0` -> `null` and Talent Check must treat `null` as *unassessed*, not zero ability (D5a).
- **(Phase 3) Evidence honesty:** a resume skill is kept only if its evidence (or its literal name) is found in the resume text; otherwise dropped and listed in `extraction_notes.dropped_skills_unsupported`. Never placeholder evidence.
- **(Phase 3) Typed model errors:** all model failures raise `gemini.LLMError(kind, message, model, provider)`. Handlers show `kind: message`; secrets never appear in messages.
- **(Phase 3) `parse_resume_llm` contract:** returns `None` only when no provider is configured; raises `LLMError` otherwise. Tests patching it in `app` keep working.
- **(Phase 3) Extension fields on resume skills:** `evidence_basis`, optional `category_repaired`. Profile extension fields: `education_entries`, `extraction_notes`, `parsing_method`, `text_characters`, `notice`.
- **(Phase 4) Storage:** source of truth is always a durable store (Supabase if configured, else local JSON files). No in-process cache. Local mode is reported as `storage: local-file` / `storage_mode: local-file`, never "memory".
- **(Phase 4) Profile validation:** strict on `/api/profile`, `/api/talent-check`, `/api/skill-match` alike (one `Profile` model). Skill needs only `skill_name`; `category_code` defaults to `OTHER`, `confidence` to `low`, `evidence` to `""`, `level` to `null`. Out-of-range or non-numeric level -> 422 (not clamped). Name is required **on save only**; email is optional but must be valid if present (deviation from the original zod UI which required it; resumes may lack one).
- **(Phase 4) Edit provenance:** the server compares each save with the stored version: a changed scalar field joins `user_edited`; a removed list item/skill joins `dismissed` (lower-cased key; skills keyed `name|CATEGORY`). Merge honours both. Skills carry `source` = `resume` | `manual` (no `source` and no `evidence_basis` == manual). Merge never deletes a skill and never touches a `level`.
- **(Phase 4) Merge endpoint is stateless:** `POST /api/profile/merge-resume {profile, parsed}` returns `{profile, report}`; the client saves explicitly.
- **(Phase 5) Unassessed is not zero:** `readiness_score` = mean over ASSESSED categories; `null` when none; `readiness_floor` (unassessed=0) and `score_range` always shown; `provisional` when <6/12 assessed. Candidate level per category = max explicit level. Unassessed rows have `candidate_level: null`, `gap: null`, `status: "unassessed"`. Statuses are now snake_case (`meets_bar|close_gap|priority_gap|unassessed`); old display strings are gone. Contract deviation (documented): `candidate_level`/`gap`/`readiness_score` may be null.
- **(Phase 6) Matching order & honesty:** exact -> alias -> guarded fuzzy; every matched JD skill reports `match_type`, `matched_with`, `similarity`. Fuzzy counts toward `match_score` but is listed and `exact_only_score` is always returned. No substring matching, ever. Missing skills keep the JD's own spelling. Fuzzy is deterministic string similarity only; an LLM semantic matcher was NOT added (agent harder to debug than the problem; per brief).
- **(Phase 7) Level input:** blank = `null` = not assessed; entering a value clamps to integer 1-10 (0 is no longer enterable). Talent Check button is always enabled; Skill Matching button is disabled until a JD is analysed. New analysis clears any previous match result.
- **(Phase 7) Frontend structure:** all HTTP goes through `src/api.js::call` (one error path, readable pydantic errors); `App.jsx` owns state and handlers; components are presentational. Frontend flow test is opt-in via `RADIX_TEST_API` so `npm test` never fails merely because no server is up.
- **(Phase 6) JD handle:** `jd_id` (uuid from `/api/analyze-jd`) is stored in `backend/data/jds/` (override `JD_STORE_DIR`, git-ignored, zip-excluded). A stored JD overrides client lists. Supabase `jd_analytics_results` lacks a `jd_id` column, so only its row `id` resolves there (no migration added).

- **(Phase 9) Docs policy:** `docs/INTEGRATION_AUDIT.md` may only contain results that were produced by running something, each tagged with its session. Old audit files are bannered SUPERSEDED, not deleted. README is the single source for run instructions.
- **(Phase 9) No LangChain / no agent** is a recorded, deliberate deviation from the brief's "LangChain or an LLM agent" wording (direct typed Gemini client; brief itself says plain code beats a hard-to-debug agent). Presenter should say so if asked.
